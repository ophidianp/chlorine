# Isotope – instructions for Claude Code

Isotope is a Fabric mod that lets mods built for one Minecraft 26.x release
load on another (for example a 26.1.2-only mod on 26.3, or a 26.3 mod on 26.2).
It rewrites the other mod's bytecode, mixin strings, access wideners and
metadata at game start. Most of the code is AI-assisted; the maintainer tests
every build and wants to learn the code, so explain non-obvious changes.

## Branch (important)
- This branch (`isotope`, in the `ophidianp/chlorine` repo) holds ONLY Isotope.
  It shares no history with `main` (Chlorine) or the website branch and will
  move to its own `ophidianp/isotope` repo later. Never merge it into `main`,
  never copy Chlorine files in, never create extra branches unless asked.
- Mod ID / package: `isotope` / `com.isotope`. Brand: violet `#B79CF0`,
  white atom glyph (`branding/icon.svg`).

## How it works (read before changing anything)
1. `boot/IsotopeAdapter` is a Fabric *language adapter*. Fabric Loader
   instantiates it in the middle of mod setup - the only hook early enough to
   add mods. It calls `boot/Bootstrap`.
2. `Bootstrap` finds jars in `<game>/isotope/mods/` (NOT the normal mods
   folder: Fabric rejects wrong-version mods before any mod code runs).
3. `rewrite/JarRewriter` unpacks each jar (and jars nested in it), detects the
   version it was built for, and runs every class through one `Hop` per
   version step using the tables in `src/main/resources/isotope/`.
4. `link/Linker` + `link/MixinCheck` resolve every reference against the real
   running game and write what is still broken to `isotope/report.txt`.
   `link/StartupPath` follows the mod's initializer to find problems that are
   certain to crash on launch.
5. `boot/LoaderBridge` registers the rewritten jars with Fabric Loader by
   reflection. ALL loader-internals access lives in that one file.

## Rules
- Isotope's own code must never reference a Minecraft class. It only uses
  Fabric Loader and ASM (both provided by the loader). That is what lets one
  jar run on every 26.x. `LoaderBridge` is the only file allowed to import
  `net.fabricmc.loader.impl.*`.
- Redirect tables (`*.redirects`) are GENERATED by `com.isotope.tools.DiffGen`
  from Mojang's jars (`tools/fetch-jars.sh` then `tools/regen.sh <dir>`).
  Never edit them by hand and never guess a rename; if a rule is wrong, fix
  the matcher.
- Hand-written rules go in the matching `*.manual` file (same format, merged
  at load time, survives regeneration). Each needs a comment with the
  evidence, checked with `javap` against both jars (example: the PushReaction
  usage counts). Stubs (`s m|f ...`, calls get null/0) are only for members
  whose whole system the game removed so nothing reads the value; never stub
  something just to make a crash go away.
- Loading policy: "class changed shape" and "fails at startup" problems keep
  a mod from loading unless `load-mods-with-fatal-problems=true`. Before
  claiming a prediction works, confirm the crash happens with it switched off.
- Never commit Mojang's jars or third-party mod jars.
- Adding a game version: add it to `isotope/versions.txt`, fetch its client
  jar, run `tools/regen.sh`, commit the new tables and `.hier` file.
- A rule that is "probably right" is worse than no rule: a wrong redirect
  silently calls the wrong method. Unresolved references are reported to the
  player; wrong ones are not. Keep the matcher conservative.
- Nothing in `Bootstrap` may crash the game. Catch, log, continue.

## Build and validate
- Java 25, Gradle 9.7 wrapper, plugin `net.fabricmc.fabric-loom`, mojmap, NO
  remap (never add `remapJar`, yarn or intermediary).
- `./gradlew clean build` (always clean; a shrinking error count without
  clean is unreliable). Unit tests: `./gradlew test`.
- Offline check without a game:
  `java -cp <runtime classpath> com.isotope.tools.Cli --game <mc.jar> --target 26.3 --lib <fabric-api.jar> --out <dir> <mod.jar>...`
- Validation order: clean build -> unit tests -> `Cli` against real mods ->
  dedicated-server boot to `Done` with old mods in `isotope/mods` (grep the
  log for `Isotope`, `FAILED during APPLY`, `was not applied`) -> real client
  run. A server boot does NOT exercise client classes or client mixins of the
  rewritten mods; say clearly when a client test is still needed.
- When Fabric Loader updates, re-check `LoaderBridge` against the new loader
  source (`FabricLoaderImpl.mods`, `modMap`, `adapterMap`,
  `ModCandidateImpl.createPlain`, the order of calls in `Knot.init`).
